fix(safety): 匿名面的节流闸门从未执法 —— 今天跑到 79 次的原因

## 实测到的真问题

`classifyAccountState` 里 `isCredentialFreeSurface(provider)` 直接
`return AVAILABLE`，于是**每日上限、每小时上限、提交间隔三者对豆包匿名面全部失效**。

容器内直接调用分类函数验证：

    accountHourlyLimit   = 6        （env 里的真实值，不是代码默认的 10）
    accountDailyLimit    = 40
    runs_today           = 79
    dateKeyOf(...) === accountDayKey(now) → true   （日期键没问题）
    runsToday >= limit   → true      （判据算出「该拦」）
    classifyAccountState → available ← 函数说「放行」

旁证：
- worker 日志里「已达每小时上限」与 `job-delayed` 都是 **0 次**
- 而按滑动 60 分钟窗口重建，今天的计数**最高 17**（上限 6）

也就是说今天能跑到 79 次，正是因为这道豁免。配额闸门形同虚设。

## 原注释的理由不成立

原判断是「匿名面没有账号可烧，所以配额检查对它是多余的」。

但**账号额度本来就是我们内部的计数器，平台不看它**。
平台看的是同一出口 IP + 同一行为模式 —— 而那正是会被限速的东西。
今天的证据链完整：

    单一出口 IP + 匿名访问 + 每 2 分钟换一个全新设备身份
    → 引用数从平均 9.3 条单调归零到 0
    → 而成功率（4–6/10）与答案字数（~1150）都没变
    → expected_citation_count=0 说明平台自己没渲染引用角标

「烧不掉账号」不等于「不需要节流」。

## 但没有一刀切给所有匿名面

`risk-control.test.mjs` 里那条
「a credential-free surface is exempt from the caps」是**实测支撑**的：
2026-09-14 千问匿名面在四道闸门全部触发时仍然正常，至今没有限速迹象。
给它加节流属于凭空收紧。

所以引入 `ANONYMOUS_SURFACES_THAT_RATE_LIMIT = new Set(["doubao"])`，
判据是**有没有直接的降级证据**，不是「是不是匿名面」。
新增平台必须先有证据 —— 测试里锁住了这个集合当前只能是 `["doubao"]`。

## 顺带修了一处判定顺序问题

匿名面分支在 `paused_at` 检查之前返回，导致「已暂停」的账号被报成「超额度」。
暂停是运维的显式意图，额度只是自动节流 —— 自动的判在前会让运维看到错误原因、
恢复动作也走错分支。所以把暂停检查提到匿名面分支的最前面。
