# OneGl 多平台代理池与浏览器复用路线

可以接代理池。建议豆包、千问、文心、智谱共用代理资源，按「平台 × 实际出口 IP」分别调度，并保留账号预算。使用稳定出口和复用浏览器来降低成本；切换出口只在任务边界进行。不能把增加代理数量当作增加平台允许额度，也不能承诺消除风控。

状态：设计完成，未实现、未修改运行配置、未连接代理商。核查日期：2026-10-15；代码基线：`eabb5bb`。配置观察仅来自本机 `.env`，未核查服务器生效配置。开发工时为工程估算，运行效果需小规模试点验证。

**2. 共用代理池，分别核算厂商与账号**

建议先使用两个可保持出口稳定、目标平台可达的代理作为试点。平台不独占代理；同一代理可同时为不同平台服务，具体并发由预算和机器资源共同决定。

```text
代理 A ── 豆包账号组：独立预算与冷却
       ├─ 千问账号组：独立预算与冷却
       ├─ 文心账号组：独立预算与冷却
       └─ 智谱账号组：独立预算与冷却

代理 B ── 同样按平台划分；用于稳定分配和网络故障恢复
```

| 层级 | 分组方式 | 作用 |
|---|---|---|
| 平台总预算 | 安装实例 + 平台，所有访问形态共同累计 | 多账号、多代理仍共享总请求预算；换 IP 不清零。样本统计仍按访问形态分开。 |
| 账号预算 | 平台 + 账号；匿名面另有明确身份键 | 保留账号并发、小时/每日上限和限制状态。 |
| 出口预算 | 平台 + 观测到的实际出口 IP | 同厂商、同出口的多个账号共同限流；豆包冷却不自动冻结千问。 |
| 网络健康 | 代理端点与线路 | 连接失败、407、线路故障单独处理，不把业务拒绝一律判成坏代理。 |
| 机器容量 | Worker 主机 | 限制浏览器数量、内存和排队量，防止本机过载被误诊为平台风控。 |

要记录「实际出口」，不能只看代理地址：两个不同的代理入口可能落到同一出口；一个入口也可能在服务商侧更换出口。绑定和预算必须处理这两种情况。

建议把出口绑定到 `(platform, account, accessMode)`；同一账号会话保持稳定出口。匿名任务也不能通过创建新本地账号名重置平台预算。代理租约临近到期或需要维护时，先停止派发、等待当前回答与引用采集完成，再重建会话。新任务开始前，剩余稳定出口时间应覆盖最大任务预算和收尾余量；不足则先续期或延后任务。租约应有续期、崩溃回收和所有权校验。

登录态账号先保持单账号单并发。不同厂商可以并行；同厂商同出口的多个账号先串行提交，再依据可用性和既定额度调整。共享出口是资源分配方案，「任何数量的账号都不会受影响」不是已验证事实。

**3. 如何复用当前浏览器，以及什么时候换出口**

保留现有 Camoufox 和 Playwright，不先更换浏览器技术栈。第一版采用浏览器进程级代理：同一租约下，页面导航、资源、流式回答和引用采集保持同一线路。Chromium/Firefox 的 context 级代理是可选的后续优化，先用实际运行版本验证隔离与认证行为。

| 环节 | 建议行为 | 验收方式 |
|---|---|---|
| 建立会话 | 将代理接入配置、Camoufox Python 参数、Node 的 `firefox.launch()` / 普通 launcher；逐项核对参数是否被中间层丢弃。 | 通过浏览器访问受控出口检查服务；记录出口、代理 ID 和认证结果。配置了必需代理却连接失败时，不静默直连。 |
| 复用浏览器 | 延续现有 `sessions` 和 `sessionCreating`，缓存键包含平台、账号、槽位及租约版本。健康会话继续使用，限制空闲驻留数量。 | 记录冷启动次数、启动耗时、常驻内存和异常关闭率；同一槽位不会重复建进程。 |
| 开始下一问 | 优先走已验证的新对话动作；需要更强隔离的平台才换 context。保留必要认证状态，验证旧答案确实清空。 | 回归现有新对话、回答归属和引用提取测试。不能把完整 `storageState()` 搬过去后声称清掉了所有站点状态。 |
| 页面操作 | 等待明确的输入可编辑、按钮可用、提交已确认、首字出现、生成结束等状态。截图与完整 DOM 主要留给异常和抽样审计。 | 分解页面就绪、提交、首字、生成和引用采集耗时，减少重复导航和重复点击。 |
| 复用业务结果 | 同一份新鲜采集结果可支撑多个报告；缓存键含平台、访问形态、模型/版本、问题、地区与时间窗口。 | 缓存命中不冒充独立的新采样；真实零引用仍进入报告分母。 |

本机目前每 2 问重启的策略需要单独评估。先固定代理、问题集合、速率及访问形态，再对照现有策略与更长会话；不要同时改 IP、并发、重试和指纹参数。试点若证实延长会话保持质量、减少启动耗时，再扩大范围。保持环境设置一致，按资源健康回收浏览器。

| 观察到的情况 | 动作 | 是否自动换出口 |
|---|---|---|
| 代理连接失败或认证失败，且确认尚未向平台提交 | 标记线路/配置异常，有限次数恢复；按绑定策略在新任务开始前选择可用线路。 | 可以进行网络故障切换；认证配置错误先修配置。 |
| 明确 429 或平台频率限制 | 遵守 `Retry-After` 或平台说明；无说明时采用保守退避。共享冷却必须约束后续任务，而不是只让当前请求 sleep。 | 不用切换来立即重发或重置预算。 |
| 验证码、账号限制或登录失效 | 暂停相应账号/访问路径，保留现场，沿用现有人工处理流程。 | 不自动换出口继续撞击。 |
| 已提交但首字超时、流中断，无法确认平台是否处理 | 标记为提交结果不确定，保留证据；在既定预算下决定是否补采，禁止即时重复提交。 | 不把换出口当作默认重试。 |
| 回答正常但没有搜索或引用 | 如实保存访问形态、搜索迹象和引用状态；用固定样本对照判断。 | 不为追求有引用而换出口重抽样。 |

这里的「熔断」是对持续异常的路径暂停调用。网络故障可以在冷却后探测恢复；验证码和账号限制继续使用人工恢复条件。路径状态与账号状态分开，避免把一个厂商的问题扩散成整个池不可用。

**4. 最小实现与开发顺序**

在 Worker 与浏览器创建之间增加一个会话调度模块，向调用方提供两个主要操作：`acquire` 返回可运行会话、延后时间或人工阻断原因；`finish` 上报结果并释放本次任务的占用，健康浏览器可继续驻留。租约续期、出口选择、共享预算和健康状态封装在模块内。

PostgreSQL 保存代理端点、绑定规则和审计记录；凭据只保存安全引用或加密值。Redis 负责运行期租约、预算和冷却。继续复用现有账号分布式锁与 BullMQ 队列，不新增第二套任务系统。

任务未获预算时，直接进入延迟队列，不占着浏览器槽位和数据库连接等待。准备就绪后在真正提交前再原子确认预算；同一个任务的重复领取和重试不能重复扣同一提交记录。必须保留实际发送尝试的计数，不能因采集失败返还已经消耗的请求额度。

BullMQ 的内置全局限流约束同一队列的 Worker；当前队列按平台与账号拆分，单独给各队列加 limiter 不能解决多个账号共享出口的问题。共享出口预算需要独立的 Redis 原子操作。不要套用旧版本的 `groupKey` 示例。

| 阶段 | 工作 | 验收条件 | 估算 |
|---|---|---|---|
| 1：建立基线 | 核对服务器生效配置，记录请求阶段、冷启动、访问形态、实际出口和有效采样成本。 | 能区分本机拥堵、代理失败、提交失败、限流和真实零引用；不先提高请求量。 | 2–4 小时 |
| 2：单个固定代理 | 新增代理配置，贯通 Camoufox/Playwright、人工登录与 Worker。 | 出口可验证；代理故障不静默直连；换 context 仍保持绑定；凭据不进日志。 | 4–8 小时 |
| 3：共享代理池 | 接入静态端点列表、稳定租约、平台/账号/出口预算和分类冷却。 | 两个 Worker 共享同一出口也不超预算；豆包受限不冻结正常千问；换 IP 不清零账号和平台预算。 | 8–16 小时 |
| 4：复用与可观测性 | 健康浏览器复用、空闲回收、提交前延迟调度和仪表数据。 | 会话串用、重复提交、凭据串写为 0；引用与答案归属测试继续通过；比较冷启动和有效采样成本。 | 4–8 小时 |
| 5：小规模试点 | 两个稳定出口，多个平台分别记录，同地区同访问形态分组，保持总预算。 | 只接受有数据支持的吞吐/成本改善；发生明确限制及时暂停，不把新增 IP 当扩量依据。 | 24–48 小时观察 |

预计开发投入 18–36 小时，另需 24–48 小时观察。假设已有可用代理、服务器部署权限和可运行的测试环境；代理采购、供应商沟通和平台人工恢复时间另计。

主要修改位置是 `src/config.js`、`src/browser.js`、`src/worker.js`、`src/accounts/safety.js` 和 `src/api/remote-auth.js`；必要的代理/租约表通过现有 migration 流程引入。提交前许可还需要接入各 provider 的实际发送位置。通用配置、供应商字段映射和管理接口已在 `docs/2026-10-15_proxy-pool-interface-v1.md` 定义，仍属于未实现的设计，不能当成已经可用的配置键。

**5. 如何判断这套方案值得继续投入**

| 指标 | 正确口径 |
|---|---|
| 有效采样效率 | 满足本次采样合同的独立样本 / 浏览器占用时间；真实零引用可以是有效样本。 |
| 重复成本 | 实际平台提交次数 / 计划独立问题数；持久化重放与重新向平台提问分开计。 |
| 可用性 | 按平台、账号、实际出口和访问形态拆分成功、429、验证、首字超时及线路失败。 |
| 浏览器成本 | 冷启动次数与耗时、峰值/稳定内存、代理流量、空闲驻留时间。 |
| 数据可比性 | 不混合匿名/登录态、不同地区和不同时间条件；不删除零引用来美化引用率。 |

如主需求是生成文本，应另行评估官方 API 的吞吐与费用；消费者网页的搜索、引用与可见度观测要保持网页样本口径，不能用 API 回答替换后合并统计。

公开接口依据已于 2026-10-15 核对：Playwright Network 说明代理可按浏览器或 context 配置；BullMQ Rate limiting 说明同队列共享限流和 429 手动冷却，且 3.0 起移除了旧的 group keys；RFC 6585 定义 429 及可选的 `Retry-After`。本机代理字段还核对了 `node_modules/playwright-core/types/types.d.ts:25912`。
